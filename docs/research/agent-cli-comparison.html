Terminal Coding Agent · 软件工程视角

CLI 不是 agent,
它们是 agent 的 runtime

对比 Claude Code / Codex CLI / opencode 三个 control plane。 "谁更快"的正确形式不是"谁的模型更强",而是:哪个 runtime 的每轮 RPC 开销更低, 以及它往模型的工作集里塞了什么。

定位修正:control plane 的四项职责

agent 是模型;CLI 是 runtime / driver,承担下面四件事。

01

反序列化

把模型输出的意图解析成可执行调用。文本 → 结构化调用是每次往返的固定成本。

02

授权

施加 capability。审批若落在热路径上,吞吐上限就是人的响应时间。

03

执行并回灌

执行调用、捕获结果、重新序列化后写回上下文。决定工作集里放什么。

04

状态检查点

上下文超限时做有损压缩。损失率取决于被压缩内容的性质。

结论先行。Claude Code 的优势来自少走弯路,不是跑得更快: 它把 21.0% 的调用分流到意图级工具,每个任务只花中位 5.0 次 RPC; Codex 100% 压在命令式原语上,连读文件都要现编 shell,中位 13.1 次。 而两者上下文里"模型自述"的占比是 0.9% vs 15.1% —— 这解释了长任务为何漂移。

教科书级的反模式

每次空轮询都是一次完整的模型往返:上传请求 → 模型生成 → 工具返回。正确写法是 await 一个 future / 完成通知。Codex 自己有 spawn_agent / wait_agent 这些异步原语 —— 主循环只是选择了轮询。占全部调用 13.8%,100% 是纯等待。

三个 harness,三个目标函数

  • Codex — 偏全量回归,验证/编辑比 1.9:1。优化缺陷逃逸率。
  • Claude Code — 偏定向验证,比值 0.9:1。优化交付延迟。
  • opencode — 写 94 个测试 + 跑全量套件(对照:Claude Code 73 个 + 只验改动的)。买的是回归安全边际,代价是 makespan。

这是 CI 的两种策略。两个不同的目标函数,不能拿同一个指标衡量。

MECHANISM 1

假设残留

被写进工作集的假设此后每轮都被重新加权。模型没有"撤销"语义,只看到断言躺在那里。

MECHANISM 2

叙事惯性

第一人称向前推进的文体,让"继续跑偏"显得自然,回到原任务反而像跑题。

MECHANISM 3

单调累积

"模型以为自己在做什么"与"实际真相"的比例单调上升,直到工具结果到来。

OUTCOME

漂移

工具结果能重置事实,但重置不了故事。上下文与原始任务逐渐脱钩。

三个工程后果

  • 非幂等 —— 同一个任务在第 1 轮和第 30 轮行为不同,取决于工作集里堆了多少自述。系统失去"重放即复现"的性质。
  • 自指正反馈 —— 模型读到自己上一轮的假设 → 假设被重新加权 → 下一轮更倾向沿用。控制论上是正反馈,LLM 上叫 confirmation bias amplification。
  • GC 回收不了活着的错误 —— 上下文压缩能回收冗余,但回收不掉"still alive 的错误断言"。

注入上下文:与 prompt injection 同源

Claude Code 另有 1201 条 harness / model 撰写的注入内容(2602 KB),含 stop_hook_summary 583 条、away_summary 251 条。 机制上和 prompt injection 同源,只是来源是自己,而且被当作可信状态采信 —— 一次错误的自我总结会被后续每一轮无条件继承。

核心结论

对事实做有损压缩,丢的是冗余;对叙述做有损压缩,丢的是原始任务。 故事在摘要里会被改写、软化,甚至把原始诉求丢掉;状态清单不会。 而且 Claude Code 的检查点输入本身已被上一节的注入内容污染 —— 等于压缩前先做了一次不可信的数据规整。

可自动化性

没有彻底关闭人工确认的开关,就没有可自动化性,只有吞吐上限 = 人的响应时间。 这是无人值守流水线的先决条件,不是优化项。

方法论:Goodhart 定律

"Claude Code 更快"是代理指标被当成目标的经典案例。

Builder.io 那个对照测的不是"效率",它测的是两个不同的程序: 生成草稿 vs 生成草稿 + 全量 QA + 94 个测试。 差的那部分时间里,绝大部分是被测系统替用户承担的验证工作。 把它记成"慢",等于把质量保证成本从账上划掉了 —— 这是成本归因错误,不是性能差异。

正确的问题

不是"谁更快",而是:"在什么工作负载下,哪个 runtime 的每轮 RPC 开销更低、上下文污染更少 —— 以及我愿意为缺陷逃逸率付多少 makespan?"

可证伪的工程假设

若漂移源于"自述回灌"而非模型能力,则降低 Claude Code 的自动压缩窗口 (--autocompact 100k,低于默认 auto)会单调地降低漂移率 —— 因为检查点的原料里叙述占比更小、且更早被压掉。

测出来 → 机制解释成立;测不出来 → "自述回流"只是相关而非因果,得换方向找(比如 harness 注入通道,或工具粒度本身)。

必须说明的局限

  1. 漂移本身没有被直接测量。本报告测的是预示漂移的结构;漂移率需要人工标注或 LLM-as-judge。"Codex 不易漂移"是现场经验,机制解释与之相容。
  2. 任务单位不完全对等。Codex 每会话 2.8 个任务 vs Claude Code 每会话 13.3 次输入,后者混入大量短追问。"13.1 vs 5.0" 建议按七折理解;工具构成的差异不受影响。
  3. 二进制字符串探测是间接证据。能证明标识符存在,不能单独证明它被暴露为工具(靠 *Tool 后缀与集合自洽性提高可信度)。
  4. 外部对照实验时效有限。Builder.io 用 Sonnet 4.5、单仓库、每任务单次、n=4;Respan trace 采集于 2026 年 4 月;opencode 版本快照 1.18.31,发布节奏很快。
  5. 本机状态占用存疑。opencode.db 单文件 5.94 GiB,推测与启动延迟相关,但未实测启动耗时。对照:~/.claude 1.6 GB、~/.codex 4.5 GB。
  6. 样本来源偏斜。本机数据来自 afk-loop 编排工作流,任务形态与日常开发不同。
